# Retry, dead letters and safe replay

Every step has a retry policy: max_attempts 1–5, base_delay_seconds 1–30, max_delay_seconds 1–300 (at least base), jitter_fraction 0–0.3. Defaults are 3 attempts, 1-second base, 30-second cap, 0.2 positive jitter. The initial attempt counts toward the maximum. Delay is `min(cap, max(base * 2^(attempt-1) * (1 + jitter * random), Retry-After))`; Retry-After is capped. Due times and schedule consumption/cancellation are durable PostgreSQL records, not in-memory timers.

TIMEOUT, TEMPORARY_UNAVAILABLE and RATE_LIMITED are retryable connector failures. SQL timeout/lock timeout and transient database failures are classified safely. Validation, unsupported operations, authority review, missing ownership, permission failures, action uncertainty and unexpected internal code errors are terminal. A failed effect transaction rolls back its local effects before a separate fenced transaction records the retry or failure. No raw exception text is stored or returned.

After exhaustion, failure_behavior defaults to DEAD_LETTER; FAIL is also supported. One tenant-scoped dead-letter row per execution preserves event, execution, step, category and attempts. History includes failure and retry events; the original signed inbox payload remains evidence. A permanently invalid workflow input does not retry indefinitely.

Cancellation is immediate for PENDING/WAITING/RETRY_SCHEDULED, cancelling unfinished steps and outstanding schedules. RUNNING cancellation is cooperative at the next ownership check; serialized local effects already committed are retained. Cancellation never undoes business actions. Deactivating a workflow prevents new dispatch, not existing execution progress.

Manual replay requires executions:recover (admin, engineer or operations), valid current tenant membership, an eligible FAILED/DEAD_LETTERED execution, and JSON `{ "confirmed": true }`. It revalidates the workflow principal, rejects uncertain receipts and verifies completed action receipts against their saved output. Replay creates a new execution with root/replay_of/generation provenance, copied completed checkpoints and pending remaining steps. Local attempt budget restarts; fault simulation counts root-lifetime action attempts so an exhausted synthetic transient can recover after explicit replay. Permanent injected failures still fail. Duplicate replay requests return the same child execution. Replay of successful, active or cancelled executions is denied.

Mock connector idempotency keys are server-owned `workflow:<root UUID>:<stable step ID>`, unchanged across replay. Action receipts are unique per tenant/root/step and bind connection, operation and validated payload digest. Applied receipts are reused only for matching requests; uncertainty/digest mismatch blocks repetition. The local synthetic business effect, APPLIED receipt and step checkpoint commit atomically, so rollback/crash cannot commit one without the others.

Future external effects cannot share a PostgreSQL transaction. A provider might accept an operation before the process records its local checkpoint. That unavoidable crash window requires provider-side idempotency or an explicit UNKNOWN outcome with reconciliation before replay. This implementation makes no exactly-once delivery claim for future real providers. It has no real outbound actions and no outcome-repair endpoint that bypasses receipt checks.
